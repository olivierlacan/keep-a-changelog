# Keep a Changelog 2.0.0 — Release Checklist

> Companion to [2.0.0-PLAN.md](2.0.0-PLAN.md). Owner: @olivierlacan.
> Target release date: **2026-08-24**. Last reviewed: 2026-07-17.

The 2.0.0 page is written, built on every run, and unpublished: 1.1.0 stays
latest until `$last_version` flips. This checklist is everything between here
and a solid release, in the order it should happen.

## 1. Practice what we publish (fix before release)

Places where this repository does not yet follow its own 2.0 guidance, found
by auditing the repo against `source/en/2.0.0/index.html.md`:

- [ ] `README.md:5` still leads with the retired tagline ("Don't let your
  friends dump git logs into changelogs™"). 2.0 replaces it with "Clearly
  document the evolution of your projects." Retire it here too, or explicitly
  keep it as a historical wink — but decide, don't drift.
- [x] `README.md` badges hardcode 1.1.0 (lines 3, 19, 21). Bump to 2.0.0 at
  go-live; they are shields.io URLs, nothing updates them automatically.
  *Done in the release pull request.*
- [ ] `source/layouts/layout.html.haml:9` falls back to the placeholder string
  `"bullshit"` for pages without a frontmatter description. It can leak into
  `<meta name="description">` and OpenGraph tags, and it violates
  `docs/tone-and-voice.md`. Replace with a real fallback.
- [ ] `CONTRIBUTING.md:70-71` tells translators to duplicate
  `source/en/1.0.0/index.html.haml`. The 2.0 baseline is
  `source/en/2.0.0/index.html.md` (Markdown, not HAML). Update the workflow so
  a translator following it verbatim produces a current translation.
- [ ] `CHANGELOG.md:305` uses lowercase `[unreleased]:` while the 2.0 page's
  example uses `[Unreleased]:`. Both work (reference links are
  case-insensitive), but the example changelog we embed on every page should
  match the example we teach. Pick one casing (see #429, which asks for
  lowercase for formatter compatibility) and use it in both places.
- [ ] `docs/2.0.0-PLAN.md` still refers to the draft as `index.html.haml`
  (lines 38 and 93 area). It is `index.html.md` now. Low stakes, but the plan
  should not contradict the tree.
- [ ] The `[2.0.0] - 2026-08-24` entry in `CHANGELOG.md` is a pre-announced
  release: changes slated for a planned, dated version. The 2.0 page's
  "Structuring a release" section now blesses this explicitly — `Unreleased`
  is for changes not yet slated for a release, and announcing a dated release
  ahead of time is fine. On release day, confirm the date still matches
  reality; if it slips, re-stamp it before tagging.

## 3. Good 2.0 candidates not yet included

Open conversations that fit 2.0's notability filter (recurring question or
post-2014 shift) and are cheap, additive text. Decide in or out; anything cut
belongs in the release's "considered, deferred" list:

- [ ] [#458](https://github.com/olivierlacan/keep-a-changelog/issues/458) —
  say explicitly that sections should appear in the canonical type order. The
  page lists the six types in order but never says "use this order." One
  sentence.
- [ ] [#640](https://github.com/olivierlacan/keep-a-changelog/issues/640) —
  the page assumes Markdown but never names a flavor. One line ("CHANGELOG.md
  is Markdown; any common flavor works") closes a real ambiguity for tool
  authors. CommonMark endorsement is optional.
- [ ] [#661](https://github.com/olivierlacan/keep-a-changelog/issues/661) —
  the "Bug fixes and performance improvements" wall is the most recognizable
  bad changelog in the wild and a perfect anti-pattern example for the page.
- [ ] [#634](https://github.com/olivierlacan/keep-a-changelog/issues/634) —
  dating the `Unreleased` section. The page already blesses dated entries
  under `Unreleased` for continuously-delivered projects; one clause answers
  the remaining question (the section itself takes no date — dates belong to
  releases).
- [ ] [#638](https://github.com/olivierlacan/keep-a-changelog/issues/638) —
  the `v` prefix in tag/compare URLs. Worth one parenthetical: the links
  follow whatever your tags are named; the prefix is your call, not ours.
- [ ] Discussion "FAQ: To what extent should we include rich content?" —
  images/screenshots in entries. Unaddressed on the page; a two-sentence
  answer (text first, link out for visuals) would settle it.
- [ ] Discussion "Empty Unreleased header makes it look like the latest
  version might be unreleased" — the page already tells you to add a fresh
  empty `Unreleased` section after each release; consider one clause noting
  it is fine (and informative) for it to sit empty.

## 5. Translations at launch

**Zero of ~30 languages have a 2.0.0 translation** (`source/<code>/2.0.0/`
exists only for `en`). The moment `$last_version` flips, every other language
shows the "newer version available" notice and non-English 2.0.0 URLs serve
the contribution interstitial. That is the designed behavior, not a blocker —
but it is also launch day's biggest ask of the community.

- [ ] Regenerate the coverage dashboard (`rake translations:dashboard`) and
  spot-check `TRANSLATION_COVERAGE.md` numbers for the 1.1.0 → 2.0.0
  migration (21 sections: 1 new, 11 reworded, 9 unchanged).
- [ ] Verify the interstitial pages give a non-programmer translator a clear
  path to contribute (per AGENTS.md, this must survive the release).
- [ ] Consider a pinned issue or discussion inviting past translators to port
  their language, linking the CONTRIBUTING workflow (fixed in section 1) and
  the dashboard.

## 6. Go-live mechanics (release day, 2026-08-24)

In order, per the comments in `config.rb:22-34`:

- [ ] Confirm the `CHANGELOG.md` release date matches the actual ship date.
- [ ] Merge any outstanding `Unreleased` entries into the 2.0.0 entry (the
  changelog-pin fix currently sits there) or ship them as-is under
  `Unreleased` — decide.
- [x] Flip the published version to 2.0.0. Everything downstream — `/` and
  per-language redirects, the version selector, canonicals, "newer version"
  notices — derives from `$last_version` automatically. *Done in the release
  pull request: `VersionRouting::PUBLISHED_VERSION` is now 2.0.0 and the
  `KAC_PREVIEW_V2` machinery stays wired but inert until the next draft.*
- [ ] Tag and push `v2.0.0`. Until the tag exists, `CHANGELOG.md`'s
  `[unreleased]` and `[2.0.0]` compare links 404 — the tag is what makes our
  own changelog follow our own linking guidance.
- [ ] Create the GitHub Release for v2.0.0 (noted missing in #720). Per the
  page's own advice, derive it from the changelog entry.
- [ ] Build and deploy (`rake deploy`).
- [ ] Post-deploy smoke test: `/` → `/en/2.0.0/`; a translated language root
  → its newest translation with the notice banner; a non-English 2.0.0 URL →
  interstitial; the published date reads "August 24th, 2026"; old deep links
  to `/en/1.1.0/` still resolve.
- [ ] Close the section-4 issues, post the release announcement, and open the
  translation call from section 5.

- [ ] Unit suites green: `changelog_pin`, `changelog_release`,
  `version_routing`, `translation_coverage` (all passing as of 2026-07-17,
  with the 2026-08-24 date in place).
- [ ] Full build test (`test/build_test.rb`) against a production build.
- [ ] Playwright suites (`test/visual`): a11y, responsive, routing, visual —
  including a `KAC_PREVIEW_V2=1` pass, which is the closest rehearsal of the
  flip that exists without publishing.
- [ ] External link check over the built site (the References section and
  compare links especially).
- [ ] Clear the [Dependabot alerts](https://github.com/olivierlacan/keep-a-changelog/security/dependabot)
  (6 open as of 2026-07-17: 1 high, 3 moderate, 2 low). They are dev-only
  build dependencies — nothing ships to the static site — but a release that
  tells people to lead Security entries with a CVE should not launch with its
  own alerts ignored.
